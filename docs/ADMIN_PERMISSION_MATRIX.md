# 管理端权限矩阵

## 角色来源

现有代码中唯一真实出现过的角色编码是 `CENTER_ADMIN`（`README.md` 示例、admin-web 登录页原默认值）。项目本身没有内置角色枚举或角色管理界面。经查 **`第一阶段数据库与后端接口设计说明.md` 第 13.2 节**（"建议第一阶段预设以下角色编码"），这是项目materials中唯一对角色和数据范围有明确定义的来源，本轮权限体系严格以此为依据构建，不额外发明角色：

| 角色编码 | 说明 | 数据范围（设计文档原文） |
|---|---|---|
| `PLATFORM_ADMIN` | 平台管理员 | 全部 |
| `CITY_ADMIN` | 市级管理员 | 全部 |
| `CENTER_ADMIN` | 企服中心管理员 | 本区县/本企服中心 |
| `CENTER_STAFF` | 企服中心工作人员 | 本区县/本企服中心 |
| `DEPT_USER` | 部门办理人员 | 本部门相关事项 |
| `ROOM_ADMIN` | 会议室管理员 | 本区县会议室和预约 |

数据范围一栏对应后端 `data_scope` 字段（`ALL`/`REGION`/`DEPARTMENT`），由 `app/core/permission.py::DataPermissionService` 独立于角色强制执行——**角色权限和数据权限是两个正交的维度**，登录时仍按现有 mock-login 机制自报 `dataScope`，本轮工作只是让二者都真正被后端校验，不是把 dataScope 与角色绑死。

## 功能权限清单

设计文档没有给出细粒度的"角色 x 按钮"权限定义，以下权限编码是本轮根据现有业务流程语义归纳的最小集合（对应 `app/constants/permission.py::Permission`），未采用逐接口/逐按钮的权限编码，避免变成过度复杂的权限 DSL：

| 权限编码 | 覆盖范围 |
|---|---|
| `APPEAL_VIEW` | 诉求列表/详情查看 |
| `APPEAL_HANDLE` | 受理/退回补充/不予受理/企服中心自行办理/分派责任部门/审核部门反馈/办结/回访记录 |
| `APPEAL_DEPT_REPLY` | 部门反馈（仅此一项） |
| `MEETING_ROOM_VIEW` | 会议室/预约 列表、详情、台账查询 |
| `MEETING_ROOM_MANAGE` | 会议室资源新增/修改/启停、开放规则、材料清单、特殊日期、手工占用 |
| `MEETING_BOOKING_HANDLE` | 预约审核通过/驳回/退回补充/确认完成/标记爽约 |
| `GOV_MEETING_VIEW` | 政企约见列表/详情查看 |
| `GOV_MEETING_HANDLE` | 审核（受理/驳回/退回补正）/安排约见/修改安排/确认通知/标记完成/填写纪要/办结 |
| `DICT_MANAGE` | 字典维护 + 服务中心维护（新增/修改/启停） |
| `OPERATION_LOG_VIEW` | 操作日志查询 |
| `DASHBOARD_VIEW` | 管理端工作台统计概览 |

说明：任务要求列出的"业务办理"与"审批"在本系统里由同一批角色（企服中心）执行同一组接口完成（受理即审批，办理即处理），因此合并为 `*_HANDLE`，不再拆分成两个权限编码——拆分后不会带来任何实际可区分的角色-权限组合，反而会成为多余的维度。

## 需要业务确认的事项

以下判断在现有设计文档和代码中找不到直接依据，本轮按**最保守、最小权限**原则处理，最终应由业务方确认：

1. **PLATFORM_ADMIN / CITY_ADMIN 是否应执行日常业务操作**：设计文档只写明这两个角色的数据范围是"全部"，未说明其是否应参与诉求受理、预约审核等日常业务操作，还是仅做监督查看。本轮假设"数据范围更大的角色至少拥有下级角色的全部操作能力"（层级 RBAC 的常见默认假设），授予其与 `CENTER_ADMIN` 相同及更多的权限。**如果平台/市级管理员实际上应为纯只读监督角色，需要把 ROLE_PERMISSIONS 中这两行改为只保留 `*_VIEW` + `DASHBOARD_VIEW` + `OPERATION_LOG_VIEW`。**
2. **CENTER_STAFF 是否应具备 `DICT_MANAGE`/`OPERATION_LOG_VIEW`**：本轮判断字典维护和操作日志查看属于管理配置类操作，划给 `CENTER_ADMIN` 更合适，`CENTER_STAFF`（一线工作人员）不授予。如果业务上企服中心工作人员也需要自行维护字典或查操作日志，需要调整。
3. **ROOM_ADMIN 是否需要 `DASHBOARD_VIEW`**：工作台目前是跨三个模块的汇总视图，本轮未授予 `ROOM_ADMIN`（其职责局限于会议室域）。如果会议室管理员也需要看整体工作台，可以追加。
4. **服务中心（`service-centers`）管理权限**：设计文档未提及该资源的权限归属。本轮将其列表查看设为"任意已登录管理端用户可见"（供创建会议室时选择归属中心，且已按 A2 的 fail-closed 数据范围过滤），新增/修改/启停归入 `DICT_MANAGE`。如果服务中心信息应视为更敏感的配置项，建议单独拆出权限码。

## 前后端一致性

- 后端权威定义：`app/constants/permission.py`（`AdminRole`、`Permission`、`ROLE_PERMISSIONS`），真正的访问控制边界，通过 `app/core/permission.py::require_permissions(...)` 作为 FastAPI 依赖接入每一个管理端接口。
- 前端镜像定义：`admin-web/src/constants/permission.ts`，与后端保持完全一致的编码和映射，仅用于路由守卫（`router/index.ts`）、菜单显示（`AdminLayout.vue`）和按钮显示（`v-permission` 指令，`admin-web/src/directives/permission.ts`）。前端权限缺失或被绕过（例如直接调用 API）不会导致实际越权，因为后端已独立校验——这是本轮设计反复强调的原则："前端权限不能代替后端权限"。
